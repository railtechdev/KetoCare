# Сквозные тесты

Раздел 13 ТЗ, раздел 15 п. 22. Один сценарий из задания — «врач создаёт
назначение → родитель собирает меню → вносит дневники → отчёт формируется», три
теста про вход, проверка ширины экранов семьи, онбординг «карта → код → семья» и
**Mini App**.

## Как прогнать

```bash
make dev     # postgres и redis
make e2e     # первый раз перед этим: make e2e-install
```

API и дев-сервер кабинета Playwright поднимает сам (`webServer` в
`playwright.config.ts`), данные прогона сеет `globalSetup`. Отдельных шагов
помнить не нужно — забытый сид проявляется как «Неверный код подтверждения», и
причину по такому сообщению не найти.

Ночью то же самое гоняет `.github/workflows/e2e.yml`.

Скрипт называется `e2e`, а не `test`: `pnpm -r run test` в CI прогоняет юнит-тесты
всех пакетов, и сквозной набор попал бы туда же — в задачу без базы, без браузера
и без API. Один раз так и вышло.

## Почему сделано именно так

**Один сквозной тест, а не четыре по частям.** Смысл сценария — в стыках:
назначение врача доезжает до экрана семьи, запись семьи доезжает до отчёта
врача. Разорванный посередине, он проверяет то, что уже проверено модульными
тестами.

**Два контекста браузера, по одному входу на роль.** Врач и родитель — разные
люди с разными сессиями. Плюс настоящее ограничение раздела 11 ТЗ: `/auth/*` —
пять запросов в минуту на адрес, а переключение ролей в одном контексте давало
шесть обращений за прогон, и тест падал на защите, работающей как задумано.

**Счётчики ограничителя стираются перед каждым файлом** (`src/redis.ts`) — и
только они, ключи `LIMITS:LIMITER*`. Ослабить ограничение переменной окружения
было бы проще, но такой ключ однажды окажется включённым на стенде.

**Вход в сценарии делается запросом, а не формой.** Форма проверяется отдельно
(`tests/login.spec.ts`); прогонять её перед каждым шагом значило бы платить
временем и хрупкостью в каждом сценарии. Работает это потому, что refresh-токен
живёт в httpOnly cookie, и кабинет восстанавливает сессию при загрузке.

**Второй фактор врача задаёт сид, а не прогон.** Секрет один и тот же у сида и
у тестов (`E2E_TOTP_SECRET`), код считает `src/totp.ts` (RFC 6238 в тридцать
строк — вместо зависимости). Состояние живёт только в базе: прежде тест
настраивал фактор сам и хранил секрет у себя, и расхождение с сидом давало отказ
входа без объяснимой причины.

**Первичная настройка проверяется отдельно** — у неё своя учётка
(`e2e-doctor-setup@example.com`, сид оставляет ей секрет пустым) и свой тест в
`tests/login.spec.ts`. Повторов у него нет намеренно: событие одноразовое, и
второй заход проверял бы уже другой путь.

**Числа сверяются с «было».** База живёт дольше прогона, и ожидание «измерений:
1» сделало бы второй запуск красным. Снимок отчёта берётся до шагов, ожидание —
«стало на одно больше». План дня при этом удаляется перед прогоном
(`DELETE /menus?date=`), иначе позиции копились бы от запуска к запуску.

## Ловушки, на которых этот тест уже спотыкался

- **`aria-label` перебивает видимый текст.** «Добавить блюдо» в слоте, чекбокс
  «Съедено», стрелки дня — искать по `aria-label`.
- **Форматирование чисел разное, и внутри дневника тоже.** Кетоны печатаются
  как есть (`2.7`), а вес идёт через `formatWeight` → `Intl` с локалью ru-RU,
  то есть «15,4 кг», с ЗАПЯТОЙ. Сценарий на этом стоял красным неделю: ждал
  «15.4 кг» и не находил заголовок. В
  отчёте — через `Intl` (`2,4`), у соотношения — свой значок (`3.5 : 1`).
- **Выбор блюда — с клавиатуры.** Список закрывается по `blur`, и щелчок по
  варианту гонится с закрытием.
- **`click`, а не `check`** на отметке «съедено»: она идёт оптимистично, и
  `check` успевает увидеть ещё старое состояние.
- **Строка «Назначено приёмов в день»** появляется только когда в дне уже есть
  блюдо.
- **vite слушает `localhost`**, который на macOS разрешается в `::1`: проверка
  готовности по `127.0.0.1` не отвечает вовсе.


## Mini App (`miniapp.spec.ts`, 18.09.2026)

Главный канал семьи, пришедшей из Telegram: веб-кабинета у неё нет вовсе
(ADR-0040). До этого файла он не проверялся сквозным прогоном ни разу — только
модульными тестами с подделкой API, а подделка повторяет представления автора о
контракте, а не сам контракт. Три дефекта запуска в истории проекта были видны
ровно из живого клиента.

**Привязка чата заводится настоящими ручками.** Врач выпускает код доступа, бот
гасит его сервисным токеном (`/auth/access-codes/activate-telegram`) — тот самый
путь этапа Б, которым приходит семья. Запись в обход ручек проверяла бы Mini App
на состоянии, которого продукт создать не умеет.

Своим остаётся одно — **подпись строки запуска**: её делает Telegram, заменить
его в прогоне нечем. Алгоритм из документации Telegram, тот же, что в
`infra/scripts/miniapp_dev_link.py` и в тестах API; сервер остаётся единственным,
кто подпись ПРОВЕРЯЕТ. В CI для этого задан фиктивный `BOT_TOKEN`: подпись
считает прогон, проверяет сервер, и обоим нужен один и тот же токен.

Размер — телефонный (390 x 844): Mini App живёт во встроенном браузере Telegram
и другого не видит.

### Ловушки этого сценария

- **День берётся завтрашний.** Сегодняшний пишет `journey`, база общая, воркер
  один — два сценария на одной дате мешали бы друг другу, и падение читалось бы
  как ошибка приложения.
- **Пациент берётся у РОДИТЕЛЯ**, у него ровно один ребёнок. У врача их
  несколько — `onboarding` заводит нового при каждом прогоне, — и `limit=1` даёт
  произвольного, к которому семья доступа не имеет. Это стоило отказа 403 на
  создании блюда.
- **Область сессии проверяется, а не только её открытие.** Привязка живёт в базе
  между прогонами; привязанная однажды к чужому ребёнку, она молча уводила весь
  сценарий на чужую карту — экран работал, блюда не находились. Теперь помощник
  сверяет `patient_id` сессии с ожидаемым и при расхождении снимает привязку
  ручкой отвязки.
- **`/auth/telegram-init` ограничен пятью обращениями в минуту**, а один прогон
  тратит их законно: проверка привязки, запуск, перезагрузка. Без сброса лимита
  тест падал на «Не удалось открыть кабинет» — то есть на 429, который на экране
  выглядит как сбой сессии.
- **`click`, а не `check`** на отметке «съедено»: у `check` своё короткое
  ожидание, а отметка живёт на сервере.
- **Mini App прогревается в `global-setup`** вместе с кабинетом: он поднимается
  отдельным сервером и платит за холодный старт Vite отдельно.
