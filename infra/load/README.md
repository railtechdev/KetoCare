# Нагрузочный прогон

Раздел 15 п. 22 ТЗ: сто одновременных пользователей. Профиль — `locustfile.py`,
запуск — `make load`.

## Как прогнать

```bash
make dev          # postgres и redis
make seed-e2e     # учётные записи и ребёнок, по которым ходит профиль
make api          # в отдельном окне
make load         # 100 пользователей, разгон 10/с, две минуты
```

Цель по умолчанию — локальный API (`http://127.0.0.1:8001`). Другую задаёт
`LOAD_HOST`, и задавать её нужно КОМАНДЕ — как и разрешение ниже: профиль
читает окружение процесса, запись в файле окружения до него не доедет. Но **на боевой стенд прогон не гоняют**: профиль пишет записи в
дневник, и в базе останутся сотни выдуманных измерений у настоящего ребёнка —
убрать их можно только `core.tools.erase_patient`.

Это не пожелание, а отказ. Цель, хост которой не `localhost`, `127.0.0.1` или
`::1`, останавливает прогон на старте — через `StopTest`, иначе locust
проглотил бы отказ обработчика и пошёл дальше. Пройти можно только поимённым
подтверждением:

```bash
LOAD_ALLOW_TARGET=https://app.example.uz make load
```

Значением служит САМ адрес, а не «1»: подтверждение должно быть конкретным,
иначе строка в профиле оболочки снимает защиту навсегда и для любой цели.
Передавать переменную нужно КОМАНДЕ — профиль читает окружение процесса.

Оговорка: остановленный прогон завершается кодом 0 (так устроен locust в
headless), поэтому `make load` на чужой цели отрапортует успехом. Судить надо
по строке отказа в выводе, а не по коду возврата.
Прежде здесь стояла печать «ВНИМАНИЕ», после которой прогон продолжался:
правило существовало в тексте и ни в одном исполняемом виде.

## Что измеряется и почему именно это

Профиль повторяет дневную работу семьи, а не шторм по одной ручке: главная,
план дня, дневник, поиск продукта — и одна запись на десять чтений. Врач ходит
реже, но берёт отчёт за месяц, и это самый дорогой запрос из читающих.

Сознательно **не нагружаются**:

- **ИИ-ручки** — каждый вызов стоит денег из общего дневного бюджета; сто
  одновременных разборов выжгли бы его за минуту, ничего не измерив: узкое место
  там у Anthropic;
- **сборка PDF** — её делает воркер, ручка только ставит задачу;
- **вход** — `/auth/*` ограничен пятью запросами в минуту на адрес (раздел 11
  ТЗ). Первая версия профиля входила каждым пользователем, и на двадцати
  пользователях пять входов прошло, пятнадцать получили 429: измерялся
  ограничитель, а не база. Поэтому вход теперь **один на весь прогон**, а токен
  разделяют все пользователи. Если прогон падает на старте с 429 — значит,
  недавно уже входили; подождите минуту.

## Пороги

Ориентиры для пилота, а не гарантия SLA:

| Показатель | Порог |
|---|---|
| Ошибок (fail ratio) | 0 % — любая пятисотка при ста пользователях означает дефект, а не нагрузку |
| p95 на чтение (`/overview`, `/menus`, `/logs/*`) | до 400 мс |
| p95 на `/report` за месяц | до 1,5 с |
| p95 на `/products?q=` | до 600 мс — полнотекстовый запрос с GIN-индексом |

| p95 на веере сводок (`/overview (веер триажа)`) | до 400 мс, как у одиночного чтения |

### Веер сводок

Первый экран врача запрашивает сводку **отдельным запросом на каждого
пациента**: кабинет ходит в `/patients/{id}/overview` столько раз, сколько у
врача прикреплённых пациентов. Один заход на главную стоит `1 + N` обращений, и
каждое — агрегат по дневникам и меню с проверкой доступа.

#### Замер от 14.09.2026: пакетная ручка не нужна

Прежде здесь стояла оценка («22 мс на одиночном обращении, отсюда около 0,9 с на
сорока»), и она же была причиной ничего не трогать. Теперь величина измерена.

Когорта: один врач, 200 пациентов (потолок страницы — `DOCTOR_PAGE_LIMIT`), у
каждого активное назначение и две недели дневника. Ноутбук разработчика, postgres
в docker, API одним процессом uvicorn.

| N пациентов | одно обращение (медиана) | суммарная работа сервера | стена при 6 параллельных |
|---|---|---|---|
| 50 | 4-17 мс | 0,28-0,79 с | 0,10-0,21 с |
| 200 | 4-5 мс | 0,93-1,52 с | 0,35-0,46 с |

Одиночное обращение оказалось **в четыре-пять раз дешевле оценки**: 4-5 мс против
22 мс. Оценка снималась на пустой базе и одном пациенте, то есть на холодных
планах запросов.

**Задержка сети на стенде считается отдельно, и она же главная.** Стенд отвечает
по HTTP/1.1 (проверено: `curl -w '%{http_version}'` → `1.1`), то есть браузер
держит к домену около шести соединений, а полный круг до стенда — 34 мс, из них
9 мс до установленного соединения. Двести сводок это `200 / 6 ≈ 34` круга,
примерно 0,5 с; пятьдесят — около 0,13 с.

**Вывод: `usePatientOverviews` в пакетную ручку не переделывается.** Полсекунды
на потолке страницы не окупают изменения, которое затрагивает проверку доступа к
клиническим данным. Если возвращаться к теме, дешевле сначала включить HTTP/2 на
хосте кабинета — это снимает предел в шесть соединений одной директивой nginx и
не трогает ни строки кода.

Что осталось непроверенным: замер снят на локальной машине, а не на стенде с
настоящей нагрузкой, и число пациентов у врача в клинике по-прежнему неизвестно.
Двести — это потолок, который позволяет страница, а не наблюдение.

**Как повторить.** Когорта заводится одноразовым скриптом поверх репозиториев
`core` (`patients_repo.create` → `link_doctor` → `prescriptions_repo.create` →
`diary_repo.create` на две недели кетонов и веса) — такие скрипты живут в
рабочем каталоге сессии, а не в репозитории: положенные в `apps/e2e`, они не
попадают ни под prettier, ни под eslint, ни под tsc. Замер — `httpx` с токеном,
выписанным через `api.security.create_token` (вход формой тратит минуту и
спотыкается о второй фактор), по 6 и по 12 одновременных запросов, первый ответ
отбрасывается как прогрев планов.

Пороги проверяются глазами по сводке locust. Автоматической проверки в CI нет
намеренно: прогон занимает минуты и зависит от машины, а красный CI из-за
медленного раннера научил бы игнорировать красный CI.

#### Замер от 07.10.2026: оценка роста в каждой сводке специалиста

PR #282 добавил в сводку два расчёта: вчерашний недобор (всем) и пометку
«значимое снижение по ВОЗ» (`growth_significant_drop`, только врачу и
диетологу). Пометку главная врача считает на каждого пациента, то есть `N` раз
за заход, и считала её той же функцией, что раздел «Рост и вес»: весь ряд
взвешиваний (до 500) ORM-объектами, z-баллы и точки графика на каждое.

Две когорты по 200 пациентов у одного врача, назначение и две недели кетонов у
всех: **short** — две недели ежедневного веса (как в замере 14.09.2026),
**long** — год ежедневного веса с ростом раз в месяц, худший правдоподобный ряд.
Ноутбук разработчика, отдельная база, без чужой нагрузки (load average около 2).

Время сервера на одну сводку (в процессе, `build_overview`, медиана пяти кругов,
варианты перемешаны по каждому пациенту):

| вариант | short | long |
|---|---|---|
| до #282 (без недобора и роста) | 2,96 мс | 2,98 мс |
| семья после #282 (недобор) | 3,17 мс | 3,19 мс |
| специалист, #282 | 4,24 мс | **6,37 мс** |
| специалист, после правки | 3,94 мс | 4,84 мс |

Главная врача по HTTP (`1 + 200` обращений, uvicorn одним процессом, по 6
одновременных, медиана трёх заходов): до #282 — 0,47 с на обеих когортах; #282 —
0,58 с и **1,27 с**; после правки — 0,55 с и 0,75 с.

На длинном ряду #282 добавлял 3,4 мс на сводку — больше порога в 2 мс, и главная
на 200 пациентах становилась в два с половиной раза дороже. Разбор показал, что
дорог не счёт по таблицам ВОЗ (около 0,3 мс на 365 точек), а всё вокруг него:
сборка 365 ORM-объектов с подсчётом общего числа (~3 мс) и 365 точек графика с
перцентилями, которые пометке не нужны. Правка:

- ряд берётся тремя столбцами (`diary.weight_series`) — те же записи и тот же
  порядок, что у выдачи дневника, это держит тест в `packages/core`;
- пометка (`growth.significant_drop_for_patient`) идёт тем же путём, что раздел
  карты — та же загрузка, тот же ряд z-баллов, тот же выбор исходного значения, —
  но без точек графика. Совпадение с разделом проверено на 5000 случайных рядах
  (старый и новый расчёт дали одинаковый ответ раздела и пометки) и закреплено
  тестом API на случае «вес в норме, снизился только рост».

Остаток — 1,9 мс на длинном ряду и 0,8 мс на коротком: три запроса (пациент,
ряд, дата начала терапии) и z-баллы по каждой точке. Кэш по пациенту на сутки не
делался намеренно: новое взвешивание обязано поднять пометку в тот же день, а
сверка «не устарел ли кэш» стоила бы того же запроса.

**Как повторить** — как и замер 14.09.2026, одноразовыми скриптами в рабочем
каталоге сессии: когорта прямыми вставками `WeightLog`/`KetoneLog` поверх
`patients_repo.create` → `link_doctor` → `prescriptions_repo.create` на
отдельной базе (`alembic upgrade head` с `DATABASE_URL` новой базы), «до» —
подменой `_yesterday_shortfall` и пометки роста в том же процессе, а не
откатом коммита: так варианты меряются вперемешку на одной и той же машине, и
шум соседних процессов ложится на все поровну.

## Замер от 04.09.2026

Ноутбук разработчика, postgres и redis в docker, API одним процессом uvicorn без
`--workers`. Сто пользователей, разгон 20/с, минута:

```
2190 запросов, 0 ошибок, 36,6 запроса в секунду
p50 = 10 мс, p95 = 49 мс, p99 = 150 мс (все ручки вместе)
/overview     p95 = 71 мс     /menus?date  p95 = 23 мс
/logs/ketones p95 = 24 мс     /products?q  p95 = 120 мс
/report       p95 = 150 мс    POST /logs/ketones p95 = 110 мс
```

Запас к порогам — примерно на порядок, и это при одном процессе API. Число само
по себе ничего не обещает про боевую машину, но говорит, что узкого места в коде
на этом профиле нет: медленнее всего полнотекстовый поиск продуктов и отчёт за
месяц — ровно то, что и ожидалось.

## Что делать с результатом

Всё, что вылезает за пороги, разбирается по одному правилу: сначала смотреть в
план запроса (`EXPLAIN ANALYZE`), потом в число запросов на ручку (N+1), и только
потом — в железо. Три из четырёх найденных до сих пор задержек были N+1, а не
нехваткой ресурсов.
