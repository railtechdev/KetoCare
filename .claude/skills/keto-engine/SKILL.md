# Keto Engine — процедура изменений

Ядро — единственное место, где ошибка = клинический риск. Порядок обязателен.

## Перед любой правкой

1. Прочитай `docs/medical/calculation-engine-spec.md`. Если файла нет (сейчас его нет)
   или значения нет — бери дефолт из ТЗ §6.2, помечай `# TODO(med): подтвердить`,
   добавь вопрос в `docs/medical/OPEN_QUESTIONS.md` — человеческим языком, для врачей:
   что система делает сейчас, что нужно решить, какие варианты. Технику (где живёт
   дефолт, что переписывать после ответа) — строкой того же номера в
   `docs/open-questions-tech.md`.
2. Прочитай `packages/keto_engine/src/keto_engine/constants.py`, эталоны в
   `docs/medical/reference-cases/` и тесты пакета
   (`test_reference_cases.py`, `test_properties.py`, `test_engine_internals.py`,
   `test_public_demo_matches_engine.py` — демо-калькулятор лендинга обязан
   попадать в назначение по правилу ядра; смена правила расчёта роняет и его,
   тогда правится `packages/landing`, а не тест).

## Инварианты (нарушение = ошибка задачи)

- Пакет чистый: никаких импортов из core/api, никакого I/O, только frozen dataclass in/out.
- Формула соотношения: `F = R × (P + Cnet)`, где `Cnet` — углеводы за вычетом клетчатки
  (ответ клиники 09.09.2026, вопросы 2 и 6; [ADR-0030](../../../docs/adr/0030-net-carbs-ratio.md)).
  В solve линеаризуется как `F − R·P − R·Cnet = 0`. Клетчатка вычитается ПО КАЖДОМУ
  продукту и не уходит в минус: у продукта с клетчаткой больше углеводов вычитание
  дало бы отрицательный вклад в знаменатель и завысило соотношение всего блюда.
- **Лимит углеводов из назначения (`carbs_max_g`) — по ОБЩИМ углеводам.** Две величины
  считаются по-разному намеренно, это прямой ответ клиники (вопрос 3), а не оплошность.
  Переключателя `net_carbs` не существует: клиника назвала правило, а не выбор.
- Дефолтные константы живут ТОЛЬКО в `constants.py`, каждая медицинская — с `TODO(med)`:
  энергия 9/4/4 ккал/г; допуск R ±0.15; kcal ±5%; округление масс до 1 г; мин. масса
  ингредиента 2 г. `DEFAULT_MAX_INGREDIENT_GRAMS` (5000 г) — техническая граница LP,
  без `TODO(med)` намеренно. Числа в коде движка вне constants.py — ошибка ревью.
- История версий — комментарием над `ENGINE_VERSION` в `constants.py` (сейчас 1.2.0):
  новая версия дописывается туда же с объяснением, почему minor/major.
- Допуски проверяет только `within_tolerance(dish, targets)` ядра: ответ о соотношении
  трёхзначный (`None` — у блюда нет соотношения, «сказать нечего»). API его не
  повторяет (`routers/calc.py`, `services/overview.py`), фронтенд — тем более.
- `solve` — scipy.optimize.linprog (HiGHS). При infeasible — определить нарушающее
  ограничение поочерёдным ослаблением и вернуть `InfeasibleError` с человекочитаемой
  причиной на русском («С выбранными продуктами недостижимо соотношение 4:1 — …»).
- Аллергии фильтрует вызывающая сторона; ядро о них не знает.
- `verify()` отдаёт вклад каждой позиции в `ItemAmount` (kcal и макронутриенты на её
  массу, с 0.4.0); итоги блюда — сумма этих вкладов. Вклад в браузере не пересчитывается
  — его отдаёт `/calc/verify` в `dish.items`.

## Вызов ядра из API

- `/calc/*` — тонкие обёртки, ответ несёт `engine_version`.
- **Приправы в ядро не попадают** ([ADR-0054](../../../docs/adr/0054-uncounted-seasonings.md)):
  продукт с `products.counts_in_calculation = false` отсекается до ядра одной функцией
  `api.services.composition.split` (для `/calc` — `uncounted_products`, отметка берётся
  из справочника, а не из тела). Новая дорога к ядру обязана идти через неё. Ядро и
  `ENGINE_VERSION` этим не затронуты: это свойство данных, а не формулы — не заводи
  поле «считать ли» в `Ingredient`.
- Сохранённые числа несут свою `engine_version`; сравнимы ли они с сегодняшними,
  решает только `api/services/engine_version.py` (`comparable_to_current`: значима
  лишь смена major). День другой major-версии вердикта о допуске не получает
  (`DaySummary.tolerance_gap = engine_changed`). Отсюда цена major-bump: все
  сохранённые дни теряют вердикт — указывай это в PR.

## Проверка выполнимости назначения

`max_non_fat_grams(ratio, kcal)` — не медицинское правило, а тождество: из
`F = R·(P + Cnet)` и коэффициентов Атуотера следует `P + Cnet ≤ kcal / (9R + 4)`.
Используется в `/prescriptions` для отсева арифметически невыполнимых назначений
(цель по белку выше этой величины недостижима ни при каком наборе продуктов).

**Величина ограничивает белок с ЧИСТЫМИ углеводами, а не с общими.** Клетчатка
съедает свои 4 ккал/г и не входит в знаменатель, поэтому с ней тождество даёт
`P + Cnet = (kcal − 4·Fiber) / (9R + 4)` — граница только строже, и проверка
белка остаётся верной. А вот фраза «на белки и углеводы приходится не более N г»
неверна: блюдо с клетчаткой даёт больше. Говорить надо про белок.
Добавляя подобные проверки, убедись, что это именно тождество, а не подобранный
порог: порог = выдуманная медицинская константа (нарушение правила 1).

## После правки — всегда

1. Подними `ENGINE_VERSION` (semver: fix → patch, новая логика → minor,
   изменение результатов существующих расчётов → major).
2. Прогони эталоны: `make test-engine` (один кейс — `uv run pytest packages/keto_engine -k <имя>`).
   Все эталоны зелёные. Эталонный тест упал → чини код. Менять эталон можно ТОЛЬКО по новой
   версии медицинской спецификации, и делает это человек (хук блокирует правку `docs/medical/`).
3. Property-тесты (hypothesis) обязаны сохраниться: `verify(solve(x))` в допусках;
   `scale(r, 1.0) == r`; монотонность kcal по массам.
4. Покрытие пакета — 100% строк (`make coverage-engine`).
   Пункты 1-2 проверяет хук `.claude/hooks/engine-guard.sh` сразу после правки:
   он гоняет тесты ядра и требует bump ENGINE_VERSION. Не обходи его — он ловит
   ровно то, что иначе всплывёт в CI через десяток правок.
5. В PR: что изменилось в математике, почему, ссылка на пункт спецификации/ТЗ.
