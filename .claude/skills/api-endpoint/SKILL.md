# Эндпоинт API — процедура

## Слои (строго)

router (тонкий: параметры, зависимости, коды ответов) → service (бизнес-логика) →
repository из packages/core (доступ к БД). SQL/ORM-запросов в роутерах и сервисах нет.

## Чек-лист новой ручки

1. Префикс `/api/v1`; пагинация `?limit&offset` → `{"items": [...], "total": n}`.
2. Данные пациента → зависимость `require_patient_access(patient_id)`.
   Помни: admin к клиническим данным доступа НЕ имеет; врач — только к прикреплённым;
   родитель — только к своим детям.
3. Ошибки — только `{"error": {"code", "message"(ru), "details"}}`;
   коды из фиксированного списка ТЗ §5.1 (не выдумывай новые без ADR).
4. Если действие в списке аудита (назначения, продукты/рецепты, учётные записи,
   выгрузки, привязка Telegram) — запись в audit_log с before/after.
5. Мутации клинических записей — мягкое удаление, проверка владения записью.
6. Тесты: happy path + 403 (чужой пациент) + 422 (валидация). Интеграционные, через httpx.
7. `make openapi` — перегенерируй packages/api-client; убедись что web/miniapp компилируются.
   Пока Makefile не заведён — выгрузи openapi.json из приложения и перегенерируй клиент
   тем же способом, что описан в README, а не правь `packages/api-client/src/generated/` руками.
8. Ответы `/calc/*` включают `engine_version`; бизнес-логики расчётов в API нет —
   только вызов keto_engine.

## Асинхронность

Все ручки async; блокирующие операции (PDF, AI) — задачей в ARQ, ручка возвращает job id.
