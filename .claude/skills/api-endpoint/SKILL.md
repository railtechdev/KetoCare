# Эндпоинт API — процедура

## Слои (строго)

router (тонкий: параметры, зависимости, коды ответов) → service (бизнес-логика) →
repository из packages/core (доступ к БД). SQL/ORM-запросов в роутерах и сервисах нет.

## Чек-лист новой ручки

1. Префикс `/api/v1`; пагинация `?limit&offset` → `{"items": [...], "total": n}`.
2. Данные пациента → зависимость `require_patient_access(patient_id)` (`PatientAccessDep`).
   Пациента нет в пути — `assert_patient_access(session, user, patient_id)`, а не
   репозиторий напрямую. Коллекционная ручка без `{patient_id}` берёт пациентов из
   `accessible_patient_ids` (`AccessiblePatientsDep`). Помни: admin к клиническим
   данным доступа НЕ имеет; врач и диетолог — только к тем, кого ведут; родитель —
   только к своим детям.
3. **Канал сессии и сужение.** `CurrentUser.channel` — `web`, `miniapp` или `bot`;
   токены Mini App и бота несут `patient_scope` (один ребёнок), и обе функции из
   п. 2 его уже учитывают — своя выборка мимо них открывает чужих детей. Если ручка
   в каком-то канале недопустима (выдача кодов, закрытие доступа, добавление
   ребёнка по коду), отказ — на сервере, 403 с понятным текстом. Список того, где
   канал уже различается, — дополнение к ADR-0041.
4. **Бот** ходит только по `BOT_ALLOWED_ROUTES` (`deps/bot.py`). Новая ручка для
   бота — строка там; ручка, боту не нужная, туда не попадает. Канал записи
   (`source`) ставит сервер по токену (`services/logs.py`), клиент его не передаёт.
5. Ошибки — только `{"error": {"code", "message"(ru), "details"}}`;
   коды из фиксированного списка ТЗ §5.1 (не выдумывай новые без ADR).
6. Если действие в списке аудита (назначения, продукты/рецепты, учётные записи,
   выгрузки, привязка Telegram, коды доступа, закрытие доступа, передача ведения) —
   запись в audit_log с before/after.
7. Мутации клинических записей — мягкое удаление, проверка владения записью.
   Запись, которую клиент может повторить после обрыва связи, принимает
   `Idempotency-Key` (ADR-0035).
8. **Побочные эффекты — после коммита.** Уведомление семье и любая задача очереди,
   вызванная записью, ставятся через `api.after_commit.defer(session, task, *args)`,
   а не `enqueue` внутри транзакции: иначе откатившаяся запись успевает отправить
   сообщение. Отказ очереди ответ не роняет — запись уже сохранена.
9. Тесты: happy path + 403 (чужой пациент) + 422 (валидация). Интеграционные, через httpx.
   **Ручку, которую читает другое приложение** (бот, Mini App, кабинет, воркер),
   держит ещё и тест стыка в `apps/api/tests` — он пиняет форму ответа и называет
   потребителя (как `test_miniapp_diary_contract.py`). Тесты потребителя работают
   с подделкой и повторяют представления автора, а не контракт.
10. `make openapi` — перегенерируй packages/api-client; убедись что web/miniapp компилируются
    (`make lint` и `make test` сами вызывают openapi). Файлы в
    `packages/api-client/src/generated/` руками не правятся — они генерируемые.
11. Ответы `/calc/*` включают `engine_version`; бизнес-логики расчётов в API нет —
    только вызов keto_engine.

## Асинхронность

Все ручки async; блокирующие операции (PDF, AI) — задачей в ARQ, ручка возвращает job id.
