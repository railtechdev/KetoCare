# Эндпоинт API — процедура

## Слои (строго)

router (тонкий: параметры, зависимости, коды ответов) → service (бизнес-логика) →
repository из packages/core (доступ к БД). SQL/ORM-запросов в роутерах и сервисах нет.

## Сессия и транзакция

- Сессия — только `SessionDep` (`deps/auth.py`). Она объявлена с
  `Depends(get_session, scope="function")`: `commit` проходит **до** отправки
  ответа. Со `scope="request"` (умолчание FastAPI) клиент получал 201 и следующим
  `GET` не видел своей строки. Своей зависимости-сессии не заводи; порядок держит
  `tests/test_commit_before_response.py`.
- **Задача очереди, вызванная записью** (уведомление семье, письмо безопасности и
  т. п.), — `api.after_commit.defer(session, "task_name", *args)`. `get_session`
  отправит её после коммита и выбросит при откате; отказ очереди ответ не роняет.
  `queue_service.enqueue` внутри транзакции не пиши: воркер успевает выполнить
  задачу до отката. Старые места (`routers/prescriptions.py` — `notify_family`)
  ещё ставят задачу сами — это не образец.

## Чек-лист новой ручки

1. Префикс `/api/v1`; пагинация `?limit&offset` → `{"items": [...], "total": n}`.
2. **Доступ к пациенту.**
   - `{patient_id}` в пути → зависимость `PatientAccessDep`
     (`require_patient_access`). `tests/test_patient_access_everywhere.py` обходит
     ВСЕ маршруты и падает на ручке с `{patient_id}` без неё; исключение — только
     строкой в `EXEMPT` с причиной.
   - Пациент в теле или строке запроса → `assert_patient_access(session, user,
     patient_id)` в сервисе, И строка в `BODY_PATIENT_ROUTES`
     (`tests/test_patient_access_in_body.py`) с именем существующего теста, где
     чужой пациент получает отказ. Тест обходит OpenAPI и находит любое поле с
     `patient` в имени — незарегистрированная ручка роняет прогон. Ребёнка,
     выбранного косвенно (`job_id`, `link_id`), он не видит — это на ревью.
   - Коллекция без `{patient_id}` — `AccessiblePatientsDep`
     (`accessible_patient_ids`), а не своя выборка.
   - admin к клиническим данным доступа НЕ имеет; врач и диетолог — только к тем,
     кого ведут; родитель — только к своим детям.
3. **Канал сессии и сужение.** `CurrentUser.channel` — `web`, `miniapp` или `bot`;
   токены Mini App и бота несут `patient_scope` (один ребёнок) и `tg` (привязка;
   её живость `get_current_user` проверяет на каждом запросе), и функции из п. 2
   сужение учитывают — своя выборка мимо них открывает чужих детей. Если ручка в
   каком-то канале недопустима (выдача кодов, закрытие доступа, добавление
   ребёнка по коду), отказ — на сервере, 403 с понятным текстом. Где канал уже
   различается — дополнение к ADR-0041.
4. **Бот** ходит только по `BOT_ALLOWED_ROUTES` (`deps/bot.py`): разрешающий
   список шаблонов путей **без** `/api/v1`, проверяется в `get_current_user`.
   Новая ручка для бота — строка там плюс тест стыка (п. 10); ручка, боту не
   нужная, туда не попадает. Ручки с сервисным токеном (`X-Bot-Token`), где ключ
   лимита в теле, списывают попытку `hit_bot_bucket(limit, scope, key)`
   (`ratelimit.py`) — по человеку/привязке, а не только по адресу: весь бот
   приходит с одного IP (`tests/test_bot_rate_limit.py`). Канал записи
   (`source`) ставит сервер по токену (`services/logs.channel_source`), клиент
   его не передаёт.
5. **Ошибки** — только `ApiError(ErrorCode.X, "текст по-русски", details=...)` →
   `{"error": {"code", "message", "details"}}`; коды — восемь из `ErrorCode`
   (`errors.py`), новых без ADR не заводить. Если клиенту нужно ветвиться по
   причине отказа, причина — машинная строка `details.reason` в snake_case
   (`plan_changed`, `already_here`, `nudged_recently`, `totp_reused`…), а не
   разбор текста сообщения. 401 «токен не годится» — через `auth_challenge(...)`
   (`security.py`, с `WWW-Authenticate`): кабинет обновляет сессию только по
   этому заголовку, обычный 401 (неверный пароль, неверный код) — без него.
6. Если действие в списке аудита (назначения, продукты/рецепты, учётные записи,
   выгрузки, привязка Telegram, коды доступа, закрытие доступа, передача ведения) —
   запись в audit_log с before/after.
7. **Клинические записи.** Мутации — мягкое удаление. Запись дневника правит и
   удаляет **только её автор** (`created_by == actor.id`, `_require_author` в
   `services/logs.py`, ADR-0044): ни близкие, ни ведущий специалист чужую запись
   не переписывают; запись без автора не правит никто; отказ — 403.
8. **Идемпотентность.** Запись, которую клиент может повторить после обрыва
   связи (дневник, блюда, вопрос помощнику), принимает `Idempotency-Key`
   (ADR-0035): зависимость `WriteAttemptDep` (`deps/idempotency.py` — ключ +
   отпечаток метод/путь/тело), в сервисе `services/idempotency.begin(...)` →
   `Replay` (вернуть прежний ответ) или бронь → запись → `finish(...)` в той же
   транзакции. Тот же ключ с другим телом — 422, незавершённый — 409. Образец —
   `services/logs.py::create_log`.
9. **Аутентификация** (если трогаешь `/auth/*` или вход):
   - код второго фактора на входе принимается через `totp_matched_step` +
     `users_repo.claim_totp_step` (`_consume_totp_code` в `routers/auth.py`):
     повтор того же кода — отказ `details.reason = "totp_reused"` (RFC 6238 §5.2);
     голый `verify_totp` для входа не годится;
   - неудачи входа считает `login_throttle` (почта+адрес и почта; `is_locked`,
     `record_failure`, `reset` после успеха и при смене/выдаче пароля), это не
     то же, что лимит частоты по адресу `ratelimit.py`;
   - токен несёт `sid` — идентификатор сессии, переживающий обновления; «Выйти»
     пишет его в `revoked_sessions` (`sessions_repo.revoke`), `/auth/refresh`
     проверяет `sessions_repo.is_revoked`. Новый способ выдать токен обязан
     переносить `session_id`, иначе выход его не закроет.
10. Тесты: happy path + 403 (чужой пациент) + 422 (валидация). Интеграционные,
    через httpx. **Ручку, которую читает другое приложение** (бот, Mini App,
    кабинет, воркер), держит ещё и тест стыка в `apps/api/tests` — он пиняет
    форму ответа и называет потребителя в докстроке (как
    `test_miniapp_diary_contract.py`, `test_bot_rate_limit.py`). Тесты
    потребителя работают с подделкой и повторяют представления автора, а не
    контракт.
11. `make openapi` — перегенерируй packages/api-client; убедись, что web/miniapp
    компилируются (`make lint` и `make test` вызывают openapi сами). Клиент
    генерируется — руками не правится.
12. Ответы `/calc/*` включают `engine_version`; бизнес-логики расчётов в API нет —
    только вызов keto_engine.

## Долгие операции

Все ручки async. Тяжёлое — задачей ARQ: PDF-отчёт (`render_report`, ручка отдаёт
job id) и ответ помощника (`POST /ai/assistant/messages` → 202, ответ пишет
воркер). Синхронно с таймаутом ждут только `POST /ai/parse` и
`POST /ai/recipe-draft` — они ничего не сохраняют. Ожидание дольше ~60 с рвёт
nginx: такое — только очередью.
