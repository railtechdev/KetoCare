# Архитектурный аудит: самописное, настройки, учёт ИИ

Дата: 14.11.2026. Запрос заказчика: что сделано вручную там, где есть готовые решения; какие
ключи и настройки вынести в админку, чтобы не править через код; как видеть и ограничивать
расход на ИИ («в конце концов мы не узнаем, кто привёл к большому расходу»).

Метод: проход по коду всех приложений и пакетов, по `pyproject.toml` и `package.json`, по
`.env.example`, `deploy.yml` и ADR. Ничего не запускалось и не менялось. Числа строк — `wc -l`.

## 1. Главное

1. **Самописного по недосмотру мало.** Почти везде под нашим кодом стоит библиотека (JWT,
   TOTP, пароли, лимиты запросов, очередь, таблицы, графики, формы, QR). Написано руками то,
   что либо предметное (ядро расчёта, фильтры ответов ИИ, рост по ВОЗ), либо склейка между
   библиотеками. Заменять стоит пять вещей, дополнить — четыре; список в разделе 2.
2. **Через админку сегодня не настраивается ничего, кроме учётных записей и справочников.**
   Ключ ИИ, модели, бюджет и лимиты лежат в секретах GitHub и попадают на сервер только
   выкатом. Сменить ключ или модель без разработчика нельзя. Раздел 3.
3. **Расход на ИИ записывается полностью, но его никто не видит.** Каждое обращение к модели
   уже лежит в журнале с автором, ребёнком, видом задачи, моделью, токенами и стоимостью. Нет
   экрана, нет бюджетов по группам, нет предупреждений. То есть «кто привёл к расходу» узнать
   можно уже сейчас — запросом к базе, а не из кабинета. Раздел 4.
4. **Рекомендация по ИИ:** сначала свой раздел «ИИ» в админке поверх уже существующего
   журнала и настройки в базе — это закрывает запрос целиком и не требует новых сервисов.
   LiteLLM — библиотекой внутри нашей единственной точки обращения к модели, вторым шагом.
   Langfuse — когда появится площадка, которая его потянет, и решение о том, куда можно
   отправлять тексты. LangGraph не нужен: у нас нет многошаговых агентов. Раздел 4.4.

## 3. Настройки: что вынести в админку

### 3.1. Как сейчас

Все настройки — переменные окружения (28 в `core/config.py`). На сервер они попадают из
секретов и переменных GitHub при каждом выкате (`deploy.yml`): положить значение на сервер
руками нельзя — следующий выкат его затрёт. Ещё около девяноста порогов и пределов записаны
константами в коде. В админке есть учётные записи, заявки, журнал и два справочника.

Следствие: сменить ключ ИИ, модель или дневной бюджет может только тот, у кого есть доступ к
настройкам репозитория, и только выкатом.

### 3.2. Три класса настроек

**А. Остаются в окружении.** Без них приложение не стартует или их утечка равна утечке базы.

`DATABASE_URL`, `REDIS_URL`, `POSTGRES_PASSWORD`, `SECRET_KEY`, `BOT_API_TOKEN`,
`MONITOR_TOKEN`, ключи выката и резервных копий, `SENTRY_DSN`, адреса (`WEB_ORIGIN`,
`MINIAPP_ORIGIN`, `MINIAPP_URL`), `TRUSTED_PROXY_IPS`, `TZ`, каталоги файлов.

`BOT_TOKEN` — тоже здесь: им подписывается вход в Mini App, и его смена на ходу оборвала бы
сессии всех семей.

**Б. Переезжают в админку.**

| Настройка | Сейчас | Кому нужна |
|---|---|---|
| Ключ поставщика ИИ | секрет GitHub `ANTHROPIC_API_KEY` | администратор: ввести, заменить, проверить |
| Модели по группам задач | `AI_MODEL_FAST`, `AI_MODEL_SMART` и список «быстрых» задач в коде | администратор |
| Бюджеты и лимиты ИИ | `AI_DAILY_BUDGET_USD`, `AI_USER_DAILY_LIMIT`; список задач под лимитом — в коде | администратор |
| Цены моделей | таблица в `pricing.py` | администратор (или LiteLLM, раздел 4) |
| Включение функций ИИ по отдельности | нет: выключить можно только всё, убрав ключ | администратор |
| Квота вложений на ребёнка, срок хранения удалённых фото, срок жизни ссылки на отчёт | `ATTACHMENT_QUOTA_MB`, `ATTACHMENT_PURGE_DAYS`, `REPORT_LINK_TTL_HOURS` | администратор |
| За сколько дней напоминать о визите; как часто можно «напомнить семье»; срок кода для семьи | константы в коде (3 дня, 24 часа, 7 дней) | администратор, по согласованию с клиникой |
| Контакты на сайте | `PUBLIC_CONTACT_EMAIL`, `PUBLIC_TELEGRAM_URL` | администратор. Сайт собирается статически, смена потребует пересборки — отдельная задача |

**В. Остаются в коде, и это решение.**

- **Клинические величины**: допуски ядра, границы кетонов и веса, порог затяжного приступа,
  расхождение калорийности продукта. Их меняет только медицинская команда через ADR и тесты;
  переключатель в админке сделал бы клиническое решение незаметным.
- **Параметры защиты**: сроки токенов, лимиты входа и запросов, длина кодов. Ослабить их из
  кабинета не должен мочь никто.
- **Технические пределы**: размеры страниц, файлов, составов.

### 3.3. Как устроить

1. **Таблица настроек в базе** и реестр в коде: у каждой настройки тип, допустимые значения,
   значение по умолчанию и описание. Значение из базы побеждает окружение; окружение остаётся
   запасным, чтобы стенд не лёг при пустой таблице.
2. **Секреты хранятся зашифрованными**, ключ шифрования — в окружении, отдельный от
   `SECRET_KEY`. В кабинете секрет только записывается: показываются последние четыре знака и
   дата замены. Рядом кнопка «Проверить ключ» — пробное обращение, а не ожидание первой жалобы.
3. **Каждая правка — в журнал аудита**: кто, что, было, стало (секрет — без значения).
4. **API и воркер читают настройки с коротким кэшем** (до минуты), без перезапуска.
5. **Риск, который надо назвать:** с ключом в админке взлом учётной записи администратора
   становится кражей ключа и чужим расходом. Условия: второй фактор у администратора обязателен
   (проверить, что его нельзя снять), бюджет по умолчанию не бесконечный, уведомление о замене
   ключа.

## 4. ИИ: учёт, лимиты, выбор моделей

### 4.1. Как сейчас

- **Одна дверь.** Все обращения идут через `AiClient` (`worker/ai/client.py`). Мимо него
  обратиться к модели нельзя, не переписав его. Поставщик один — Anthropic.
- **Шесть видов задач:** помощник семьи, разбор еды из текста, сводка врача, черновик карточки
  рецепта, чтение файла рецептов (с 14.11.2026) и зарезервированный разбор события.
- **Журнал `ai_jobs`** пишет каждое обращение, включая неудачные: вид задачи, кто запросил,
  о каком ребёнке, модель, входные и выходные токены, стоимость, ошибка.
- **Два предохранителя:** дневной бюджет проекта (по умолчанию 10 $) и 30 обращений в сутки
  на человека — но только для помощника, сводки и черновика. Чтение файла рецептов под личный
  лимит не подпадает намеренно: один сборник — десятки обращений.
- **Две модели:** «быстрая» для разбора еды, «умная» для всего остального.
- **Монитор** (`GET /health/ai`) видит, что ИИ отказывает, но не сколько он стоит.

### 4.2. Чего не хватает

| Пробел | Следствие |
|---|---|
| Нет экрана расхода | Сумму за месяц, по видам задач и по людям можно получить только запросом к базе |
| Бюджет один на всё | Диетолог, загружающая сборник на три тысячи строк, может исчерпать дневной бюджет, и помощник семьи до завтра ответит «лимит исчерпан» |
| Бюджет только дневной | Месячного потолка нет: тридцать дней по десять долларов никто не остановит и не заметит |
| Нет предупреждений | О бюджете узнают, когда он кончился |
| Модели и лимиты — выкатом | См. раздел 3 |
| Цены — в коде | Новая модель требует правки кода; устаревшая цена искажает бюджет |
| Промпты — файлами в репозитории | Версия промпта в журнал не пишется: нельзя сказать, каким текстом получен ответ месячной давности |
| Нет оценки качества | Золотые корпуса проверяют фильтры, а не ответы модели. Смена модели проверяется глазами |

### 4.3. Что должно быть в админке (продуктовое решение)

Раздел **«ИИ»** у администратора, четыре экрана.

**Расход.** Сегодня, за неделю, за месяц. Разрезы: по группам задач, по видам, по моделям, по
людям. Список «кто потратил больше всех» со ссылкой на учётную запись. Доля неудачных
обращений и их стоимость. По детям расход показывается специалисту, ведущему ребёнка; у
администратора доступа к клиническим данным нет, и здесь он видит человека и сумму, а не
содержание запросов.

**Группы задач.** Три группы, как вы и предложили:

| Группа | Задачи | Кто запускает |
|---|---|---|
| Технические работы | чтение файлов рецептов, черновик карточки рецепта, в будущем — распознавание сканов | диетолог, врач, администратор |
| Специалисты | сводка врача | врач |
| Семьи | помощник, разбор еды из текста | родитель |

У каждой группы: модель, дневной и месячный бюджет, лимит обращений на человека в сутки,
выключатель. Бюджет одной группы не занимает бюджет другой.

**Ключ и модели.** Ввод и замена ключа, проверка, список доступных моделей с ценами.

**Предупреждения.** При 80 % бюджета группы — уведомление администратору; при исчерпании —
понятный текст пользователю («сегодня хватит», как сейчас) и строка в журнале.

### 4.4. Готовые решения: что берём

| Решение | Что это | Что даёт нам | Цена | Вердикт |
|---|---|---|---|---|
| **Свой раздел поверх `ai_jobs`** | Экраны и настройки из 4.3 | Закрывает запрос целиком. Данные уже есть | Только разработка, новых сервисов нет | **Делать первым** |
| **LiteLLM как библиотека** | Единый вызов для разных поставщиков, карта цен, запасные модели | Независимость от одного поставщика; цены не ведём сами; один шаг до Langfuse | Одна зависимость в одном файле. Клиническая защита остаётся нашей | **Вторым шагом**, внутри `AiClient` |
| **LiteLLM Proxy** | Отдельный сервис: виртуальные ключи, бюджеты по ключам и командам, своя панель | То же, что наш раздел, плюс общий шлюз для нескольких продуктов | Ещё один сервис и своя база; панель английская, с отдельным входом; журнал расхода задваивается с `ai_jobs` | **Не сейчас.** Имеет смысл, когда через один шлюз пойдут два и более продукта |
| **Langfuse** | Трассировка каждого обращения, версии промптов, наборы для оценки, панель стоимости | То, чего у нас нет вовсе: версии промптов и оценка качества при смене модели | Свой сервер тяжёлый: ClickHouse, Redis, хранилище объектов, PostgreSQL — на одной машине с 40 ГБ диска тесно. Официальные сборки ClickHouse требуют набора команд процессора, которого у площадки нет (ADR-0014) — проверить перед решением. Облако Langfuse — тексты запросов о детях уходят третьей стороне | **После переезда на площадку, которая потянет**, и после решения, куда можно отправлять тексты |
| **LangGraph** | Среда для многошаговых агентов с состоянием и ветвлениями | Ничего: наши сценарии линейны (поиск → фильтр → модель → фильтр → сверка), шаги детерминированы и покрыты тестами | Новая среда исполнения без новой видимости | **Не нужен.** Вернуться, если появится агент, сам выбирающий инструменты |

Почему не начать сразу с LiteLLM и Langfuse, хотя это общий стандарт наших проектов: здесь
единственная дверь к модели уже построена, с журналом и предохранителями, а запрос — «видеть
и ограничивать» — закрывается экраном над готовыми данными. LiteLLM встаёт в ту же дверь без
переделки остального. Langfuse упирается не в код, а в площадку и в правила обращения с
данными.

### 4.5. Вопросы, которые решает не разработка

1. **Куда можно отправлять тексты.** Сейчас псевдонимизированные данные уходят в Anthropic.
   Облачный Langfuse — ещё одна сторона. Требования законодательства Узбекистана о хранении
   персональных данных нужно сверить с юристом клиники до выбора облака.
2. **Площадка.** Нынешний сервер не тянет ни Docling, ни, вероятно, Langfuse. Вопрос связан с
   переездом, который уже обсуждался.
3. **Кто платит и какой потолок.** Месячный бюджет и его деление по группам — решение
   заказчика; без него в админке будут стоять наши догадки.

## 5. План

| Этап | Что | Оценка |
|---|---|---|
| 1 | Настройки в базе: реестр, шифрование секретов, аудит, чтение в API и воркере. Раздел «ИИ»: ключ, модели, группы, бюджеты (день и месяц), лимиты, выключатели | 5–7 дней |
| 2 | Экран расхода: разрезы по группам, видам, моделям, людям; предупреждения при 80 % | 3–4 дня |
| 3 | LiteLLM внутри `AiClient`; цены из его карты; структурированный вывод вместо разбора JSON; версия промпта в журнале | 3–4 дня |
| 4 | `pg_trgm` для поиска продуктов; объявление зависимостей; остальные настройки из 3.2 Б | 2–3 дня |
| 5 | После решения о площадке: Langfuse (трассировка, версии промптов, оценка), Docling для PDF и сканов | оценить отдельно |
| Вне очереди | Таблица исходящих задач, общий фильтр «не удалено», генерация клиента бота | по 1–2 дня каждое |

Этапы 1–2 закрывают запрос «вносить ключи через админку, выбирать модели, ставить лимиты,
видеть, кто потратил». Этапы 3–4 убирают ручную работу, найденную аудитом.

Оценки — календарные дни одного разработчика с тестами и ревью, без учёта ожидания решений.
