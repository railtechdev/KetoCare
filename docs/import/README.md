# Импорт справочников

Раздел 15 п. 24 ТЗ: завести настоящую базу продуктов и сборник рецептов. Оба
файла — CSV в UTF-8, оба грузятся с превью: сначала отчёт, потом отдельное
решение записать.

Шаблоны рядом: [`products.csv`](products.csv), [`recipes.csv`](recipes.csv).
Открываются в любой таблице; их же можно взять за образец разметки.

## Продукты

Ручка `POST /api/v1/products/import` (роль admin), экран — раздел «Продукты» в
администрировании. Колонки:

| Колонка | Что это |
|---|---|
| `name_ru` | название; **ключ позиции** — по нему находят дубли и связывают рецепты |
| `name_uz`, `name_en` | необязательные переводы |
| `category` | название категории; она должна существовать в справочнике |
| `kcal_100g`, `fat_100g`, `protein_100g`, `carbs_100g`, `fiber_100g` | значения на 100 г |
| `source`, `source_version` | откуда взяты числа: «USDA FoodData Central», «SR Legacy» |
| `verified_at` | когда сверяли с источником, ГГГГ-ММ-ДД |

**Происхождение чисел обязательно.** По ним считают еду ребёнку, и через год
вопрос «откуда 82,5 г жира» должен иметь ответ. Поэтому `source` и
`source_version` — обязательные колонки, а не пожелание.

Что отвергается: сумма жиров, белков и углеводов больше 100 г на 100 г продукта;
значения вне физиологичных границ; калорийность выше 1000 ккал; дубли названий
внутри файла. Ошибки приходят построчно все сразу — файл правится за один заход,
а не за двадцать прогонов.

**Повторный импорт.** По умолчанию строка с уже существующим названием
пропускается с объяснением. Обновляющий импорт (`update_existing=true`)
перезаписывает значения и показывает в превью, что именно изменится у каждой
позиции; прежние значения остаются в `product_revisions`.

## Рецепты

Ручка `POST /api/v1/recipes/import` (роли admin и dietitian). Формат — **строка
на ингредиент**: состав у рецептов разной длины, и «строка на рецепт»
потребовала бы либо колонок `product_1..product_20`, либо списка внутри ячейки.

```
title,category,yield_g,servings,instructions,product_name,grams
Омлет,breakfast,120,1,"1. Растопите масло.",Масло сливочное 82%,30
Омлет,,,,,Яйцо куриное,55
```

Шапка заполняется в первой строке рецепта, дальше остаётся пустой — пустая
ячейка значит «то же, что выше». `category` — одно из: `breakfast`, `lunch`,
`dinner`, `snack`, `dessert`, `drink`.

**Продукты сопоставляются по названию** (`name_ru`), регистр и лишние пробелы не
различаются. Продукта нет в справочнике — ошибка строки, а не создание на лету:
рецепт с выдуманным продуктом посчитается, и число будет неверным. Поэтому
порядок один: сначала продукты, потом рецепты.

**Существующие рецепты импорт не переписывает.** У продуктов обновляющий импорт
есть — там приходит новая версия справочника состава. Рецепт же правит человек: у
него бывают фото, статус публикации и правки диетолога, и перезапись файлом
стёрла бы их молча. Совпадение по названию — ошибка строки.

Рецепты заводятся черновиками. Публикация — отдельное решение: то, что файл
загрузился, ещё не значит, что по нему можно кормить.

В превью видно, что посчитало ядро: калорийность и кетосоотношение каждого
рецепта. Это и есть проверка файла по существу — состав, который дал 0,4 : 1
вместо ожидаемых 4 : 1, виден до записи.

## Порядок при заведении клиники

1. Категории продуктов — экран «Продукты», блок категорий. Импорт их не
   создаёт: перечень категорий это решение о том, как устроен справочник.
2. Продукты — пробный прогон, разбор ошибок, запись.
3. Рецепты — пробный прогон (он же проверит, что все продукты нашлись), запись.
4. Публикация рецептов — по одному, после проверки диетологом.

## Пределы

Файл — до 5 МБ (это десятки тысяч строк), не больше 20 загрузок в час на адрес.
Ограничивают они не перебор, а работу: каждый запрос читает файл целиком и при
записи создаёт тысячи строк одной транзакцией.
