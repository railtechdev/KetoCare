# ADR-0084. Подбор находит блюдо, которое есть, и не сдвигает то, что уже в цели

- Статус: принято
- Дата: 2026-11-16
- Связано: [аудит ядра](../AUDIT_ENGINE_2026-11.md) (находки А1, А2, А3, А5, А7, А8, А4),
  [ADR-0083](0083-solver-aims-at-the-meal-split.md), [ADR-0058](0058-dietitian-workspace.md),
  разделы 6.3 и 6.4 ТЗ

## Контекст

Независимый аудит ядра 15.11.2026 нашёл в подборе граммовки два дефекта высокой
важности и несколько средних. Все они — продолжение жалобы диетолога «подгоняю
вручную — сбивается», которую ADR-0083 закрыл на её примере, но не в общем виде.

| Находка | Замер аудита |
|---|---|
| А1. Подбор отказывает или выходит из допуска, хотя блюдо в допуске есть | 10 % запросов с двумя закреплениями, 1,9 % приёмов 75–160 ккал |
| А2. Повторный подбор сдвигает блюдо, которое уже в цели | 54 % повторных нажатий |
| А3. Сервер отбрасывает найденное блюдо и винит «границы масс» | воспроизведено |
| А5. Калорийность приёма считается в трёх местах | 263 / 262 / 262,5 ккал для 1575 ÷ 6 |
| А7. Ответ зависит от порядка продуктов в запросе | 2,7 %, до 61 г |
| А8. Причины отказа называют не то ограничение | воспроизведено |
| А4. Тесты при покрытии 100 % не ловят 14 порч кода из 53 | замер |

Причины А1: соотношение в задаче было равенством, а допуск ±0,15 применялся только
после округления — при закреплённой массе равенство недостижимо, хотя блюдо в
допуске существует; перебор целых граммов двигал четыре продукта, не глядя на
закрепления. Причина А2: близость к набранному учитывалась только в непрерывной
задаче, а подбор всегда начинал с вершины линейной программы.

## Решение

1. **Соотношение — равенство, затем полоса.** Если равенство недостижимо,
   задача решается с соотношением в полосе допуска: сначала 0,8 допуска (остаток
   съедает округление), затем весь допуск. Порядок постановок тот же, в каком
   ценится целый состав: раскладка в допуске, затем точность соотношения.
2. **Поиск по целым граммам — три шага.** Перебор ±2 г у четырёх самых влиятельных
   свободных продуктов; спуск по грамму по всем свободным продуктам (грамм у
   одного либо грамм, переложенный между двумя) до состава, который ни одним
   ходом не улучшить; если он вне допусков — перебор шире (три продукта, ±6 г) и
   снова спуск. Закреплённый продукт не двигается и места в переборе не занимает.
3. **Ранг состава — один на весь поиск:** жёсткие границы (коридор калорийности,
   минимум белка, лимит углеводов) → соотношение в допуске → раскладка в допуске
   → расстояние до целей. Состав, нарушающий границу, тоже имеет ранг: поиск
   обязан уметь уйти от него. Следствие, которое стоит знать: когда в целых
   граммах нельзя удержать и лимит, и соотношение, подбор держит лимит и честно
   помечает соотношение «вне допуска», а не отказывает.
4. **`refine()` — шлифовка набранного.** Если набранное блюдо целиком в допусках,
   сервер не решает задачу заново, а идёт от него тем же спуском. `solve()`
   заканчивает тем же спуском, поэтому его ответ — неподвижная точка: повторное
   «Подобрать» ничего не меняет. Блюдо не в цели, с пустым полем или с дробной
   массой по-прежнему уходит в `solve()`.
5. **Продукты сортируются по идентификатору** до решения, позиции ответа
   возвращаются в порядке запроса: ответ — функция запроса, а не его записи.
6. **Найденное блюдо возвращается.** Если подбор «со всеми продуктами» не
   сошёлся, а без этого условия сошёлся и ни одного продукта не потерял, это и
   есть ответ.
7. **`meal_kcal()` — одно место, где округляется калорийность приёма.** Половина
   округляется вверх, как `Math.round` в ките; подгонка рецепта и предпросмотр
   назначения считают через неё. Совпадение с китом держит тест на стороне API.
8. **Причины отказа.** Закрепления, не дающие выйти на соотношение, названы
   закреплениями; лимит печатается как пишет человек («1.42 г», а не
   «1.41667 г»); `verify()` не принимает отрицательную массу.
9. **Тесты.** Значения допусков закреплены тестом, который их называет; обе
   стороны допуска калорийности и соотношения; свойства: неподвижная точка,
   независимость от порядка продуктов, «есть блюдо в допуске рядом с
   закреплением — подбор его находит» (свидетель ищется перебором, независимо
   от подбора); итоги перебора совпадают с `verify()` до бита.

`ENGINE_VERSION` 1.10.0, minor: `verify()` и сохранённые числа не меняются,
жёсткие ограничения те же.

## Последствия

Замер на 99 продуктах `infra/seed/products-usda.csv`, до и после:

| Сценарий | Было | Стало |
|---|---|---|
| Два закрепления, блюдо в допуске существует | 17 из 163 промахов | 0 из 101 |
| Одно закрепление | 8 из 350 | 0 из 116 |
| Приём 75–160 ккал из трёх продуктов | 29 из 1522 | 2 из 196, отказов нет |
| Приём 75–160 ккал из двух продуктов | — | 0 из 193 |
| Повторный подбор сдвигает блюдо в цели | 266 из 493 | 0 из 335 |
| То же по всей серверной цепочке (коридор → свободный поиск → шлифовка) | — | 0 из 811 |
| Ответ зависит от порядка продуктов | 8 из 300 | 0 из 335 |

Замеры «было» — из аудита, «стало» — тем же способом на новом наборе случайных
составов; скрипты аудита не сохранились, поэтому выборки разные.

- Проверка `safety-reviewer` до выката нашла, что первая редакция обещала больше,
  чем делала: ответ, найденный в коридоре вокруг набранных масс, был неподвижной
  точкой только коридора, и второе нажатие сдвигало его в 27 % таких ответов.
  Теперь каждый ответ сервера выходит через ту же шлифовку, с которой начинается
  следующее нажатие. Там же: предпросмотр назначения отвечал ошибкой сервера на
  калорийность, набранную наполовину («1» из «1500»), а шлифовка могла убрать
  продукт с массой 2 г при нижней границе меньше минимальной. Всё закрыто тестами.
- Оговорка к п. 4: ответ `solve()`, из которого подбор сам убрал продукт (нижняя
  граница меньше 2 г; сервер так не вызывает), неподвижной точкой может не быть.
- Подбор стал медленнее: 10 мс в среднем и до 36 мс на блюде из 4–12 продуктов
  (было 1–10 мс), 0,3 с на 99 продуктах. Счёт идёт в пуле потоков.
- **Остаётся:** на приёме меньше 160 ккал из трёх продуктов подбор изредка (около
  1 %) отдаёт блюдо вне допуска при существующем блюде в допуске — с честной
  пометкой, не отказом.
- **Не сделано намеренно:** логика «коридор вокруг набранного → свободный поиск»
  по-прежнему живёт в `routers/calc.py` и `services/dish_fit.py` (находка А6).
  Переносить её в ядро имеет смысл отдельно, когда поведение устоится.
- Медицинские находки аудита (белок и калории по возрасту, вес для расчёта, шаг
  граммов, сверка с KDC) вынесены клинике вопросами 59–63; допуск раскладки как
  доля цели (М3) — следующий шаг, в этот PR не входит.
