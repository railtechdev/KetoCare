# ADR-0095. Два окружения и перенос данных на боевой сервер

Дата: 28.11.2026. Статус: принято.

## Контекст

До этого дня сервер был один — test-стенд `*.ketocare.railtech.uz`, куда `main`
уезжал сам. С 17.11.2026 на нём настоящие пациенты, то есть каждое слияние
меняло боевую систему без промежуточной проверки.

Заказчик 28.11.2026 заводит два сервера у хостинга в Узбекистане:

- **боевой** — `ketocare.uz`, `app.ketocare.uz`, `tma.ketocare.uz`; данные
  стенда переезжают на него «один в один, с пользователями бота»;
- **тестовый** — `demo.ketocare.uz`, `app.demo.ketocare.uz`,
  `tma.demo.ketocare.uz`.

Раздел «Передача клиенту» в `DEPLOY.md` (решение от 06.10.2026) говорил
обратное: прод начинается с чистой базы, секреты и бот — новые. Оно принималось,
когда настоящих пациентов на стенде не было.

## Решение

1. **Окружения выката — `demo` и `production`** (GitHub Environments). `main`
   после зелёного CI едет на `demo` сам. На `production` — кнопкой, и только
   коммитом, который лежит в `main` и прямо сейчас стоит на тестовом (выкат
   кладёт в кабинет `version.txt` с коммитом, шаг выката сверяет). Флажок
   `allow_untested` снимает вторую проверку на случай аварии, первую не снимает
   ничто.
2. **Секреты приложения — только в окружениях.** На уровне репозитория их нет:
   секрет, который забыли завести окружению, GitHub молча взял бы оттуда, и
   тестовый бот заговорил бы с семьями токеном боевого.
3. **Сервер знает, кто он.** `bootstrap-server.sh` пишет метку
   `/etc/ketocare/environment`; `remote-deploy.sh` сверяет с ней имя окружения,
   пришедшее с выкатом, и чужое не принимает, не трогая рабочее окружение.
4. **Данные стенда переезжают на боевой целиком**: база, тома документов и
   архивов стирания, снимок redis (`infra/scripts/migrate-server.sh`). Секреты
   приложения и бот боевого — прежние: `SECRET_KEY` подписывает сессии и
   расшифровывает ключи ИИ, введённые в кабинете, а к боту привязаны семьи.
   Это заменяет пункты 2 и 3 прежнего раздела «Передача клиенту».
5. **Режим ожидания.** Боевой сервер поднимается заранее с меткой
   `/etc/ketocare/standby`: бот и воркер в нём не запускаются. Один токен бота
   опрашивается только из одного места — бот нового сервера отобрал бы
   сообщения у работающего и отвечал бы семьям по пустой базе, а воркер после
   пробного разворачивания копии разослал бы напоминания второй раз. Метку
   снимает перенос.
6. **Прежние имена перенаправляют на новые** (301) с боевого сервера: по ним
   закладки врачей и кнопки в старых сообщениях бота. Тестовому они не
   достаются.
7. **Тестовый сервер — без настоящих данных**: чистая база, демо-сид, свой бот,
   свои секреты, без резервных копий.

## Последствия

- Слияние в `main` больше не меняет систему с пациентами. Правило «`main`
  только через PR» остаётся: тестовый сервер тоже публичен, а боевой берёт
  коммит из `main`.
- Смена домена один раз разлогинивает сотрудников: cookie привязана к имени.
  Пароль и второй фактор прежние. Семьям в боте менять нечего.
- Конфигурации nginx в репозитории остаются написанными на имя первого стенда;
  имена сервера подставляет `bootstrap-server.sh` из `BASE_DOMAIN`.
- Монитор доступности окружениями GitHub не пользуется (задача с
  `environment:` каждые 15 минут писала бы запись о выкате): его адреса и
  токены — переменные и секреты репозитория `UPTIME_*`.
- Точка входа выката на новых серверах лежит в каталоге владельца
  (`/srv/ketocare-entry/`): в корне `/srv` скрипт не мог обновить собственную
  копию — «Permission denied».
- Внешняя копия — резервное копирование хостинга (в Узбекистане). Ночные
  шифрованные копии на боевом остаются: ими возвращаются данные одного
  пациента, снимком машины — нет.
- Сборка образов по-прежнему идёт на каждом сервере. Собирать один раз и
  раздавать образ обоим — отдельная работа.
