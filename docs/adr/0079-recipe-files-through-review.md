# ADR-0079. Рецепты загружаются из файла диетолога как он есть — через таблицу проверки

Дата: 14.11.2026. Статус: принято.

## Контекст

Заказчик 14.11.2026: врач либо собирает рецепты по одному, либо загружает файл — и во втором
случае «упирается в тупик: не имея технического опыта и видя, что загруженные рецепты выдают
ошибку, начинает судорожно искать выход и опять переходит в ручную, хотя у неё заготовлена
большая база рецептов». И шире: «основная боль диетологов — работа с данными».

Импорт (`POST /recipes/import`, раздел 15 п. 24 ТЗ) принимает одну форму файла — таблицу по
нашему шаблону, строка на ингредиент, — и отвечает списком ошибок. Файл диетолога выглядит
иначе: документ Word, заголовок — название блюда, список «Орехи макадамия (обжаренные) — 30 г»,
нумерованные шаги. Остальные её файлы, по словам заказчика, «тоже разные и на других языках»;
два из присланных — сканы, вставленные в Word. Чтобы загрузить такой сборник, его надо руками
переписать в таблицу, а потом ещё угадать название каждого продукта в точности как в
справочнике: импорт ищет по точному имени и на первом несовпадении отказывает всему файлу.

[ADR-0064](0064-editors-import-products.md) решал обратное: формат один, клиника переносит
данные в шаблон, потому что «подгонка под каждый формат завела бы в тупик». Для продуктов это
остаётся в силе — там переносятся числа, и колонка должна быть названа. Для рецептов тупиком
оказался сам шаблон.

## Решение

Файл принимается любым, а всё, чего он не объяснил сам, становится строкой таблицы с действием
на том же экране. Импорт не заканчивается ошибкой.

1. **Чтение файла.** Word (.docx), Excel (.xlsx), текстовый файл или вставленный текст
   превращаются в нумерованные строки (`api.services.recipe_file`). Формат, который не
   читается, отклоняется со словами, что делать: «сохраните как .docx», «вставьте текст».
2. **Структуру показывает ИИ, и только показывает** (`worker.ai.recipe_import`, промпт
   `prompts/recipe_import.md`, вид задачи `recipe_import`). Модель возвращает, в какой строке
   какой ингредиент, количество и единицу — как написано. Она ничего не считает:
   - граммы выводит сервер и только из единиц массы (г, кг, мг, унция, фунт). Ложка, стакан,
     миллилитр, «по вкусу» массы не получают — её вписывает проверяющий или строка остаётся
     вне расчёта. Объём в массу не переводится: плотность была бы догадкой;
   - количество сверяется с исходной строкой. Числа, которого в строке нет («8,5» → «85»),
     достаточно, чтобы строка не прошла «Принять готовые» без подтверждения;
   - способ приготовления копируется из файла по номерам строк, а не набирается моделью;
   - продукт справочника модель не называет вовсе. Она может перевести название на русский;
     справочник ищет сервер.
3. **Продукт встаёт сам в двух случаях:** в справочнике есть продукт с точно таким названием,
   или это написание уже сопоставил специалист (`product_aliases`). Всё найденное поиском —
   предложение, которое принимается щелчком: «сливки 10 %» вместо «сливки 33 %» — другое
   кетосоотношение.
4. **Название решается один раз** — для всех рецептов файла — и запоминается для следующих
   файлов и для всех специалистов: справочник общий. Три действия: выбрать продукт, завести
   новый панелью на этом же экране, не взвешивать.
5. **Не взвешиваемое остаётся в тексте рецепта** («Без взвешивания: Ванильный экстракт —
   3 капли; Соль по вкусу.»). Иначе семья готовила бы не то блюдо, что написала диетолог.
   Приправа без массы (ADR-0054) уходит туда сама.
6. **Черновик хранится на сервере** (`recipe_import_drafts`), открытая загрузка — в адресе
   (`?item=import:<id>`). Сборник разбирают в несколько подходов; готовые рецепты принимаются,
   остальные ждут.
7. **Ничего не становится рецептом без решения человека** (правило 6). Принятые рецепты
   заводятся черновиками библиотеки, как и прежде; существующий рецепт не переписывается —
   занятое название делает строку неготовой.
8. **Файл читается частями** — по задаче воркера на часть, с продолжением с того же места после
   отказа (дневной бюджет ИИ, недоступность). Суточный предел обращений пользователя на этот
   вид задачи не действует: один сборник — десятки частей; дневной бюджет проекта действует.

Прежний импорт по шаблону остаётся запасным путём с того же экрана: он работает без ИИ.

## Последствия

- Новые ручки `/recipe-imports` (те же роли, что правят рецепты). Черновик виден только автору:
  чужой — 404.
- Docling не используется, хотя общие правила разработки называют его первым выбором для
  документов: площадка стенда не тянет его числовой стек (ADR-0014), а .docx и .xlsx читаются
  стандартной библиотекой и уже стоящим `openpyxl`. К PDF и сканам вопрос вернётся.
- **Не сделано, следующий этап:** PDF и сканы (в том числе сканы внутри Word — они называются
  по имени и отклоняются), старые .doc/.xls, тот же экран для загрузки продуктов.
- **Не сделано намеренно:** перевод названия блюда и способа приготовления. Текст остаётся
  таким, как в файле; рецепт на другом языке диетолог правит сама.
- Имена людей из файла не вырезаются (остаточный риск ADR-0019): почта, телефон и ник
  вырезаются общей псевдонимизацией, имя от слова неотличимо. Файл с меню конкретного ребёнка
  загружать сюда не следует.
- Черновики не удаляются сами. Убранный автором черновик скрыт, строка остаётся; уборку
  добавить вместе со следующим этапом.
- Качество чтения проверяется на настоящих файлах клиники. На машине разработки ключа модели
  нет, поэтому промпт до выката проверен только на подделках ответа; первая проверка на
  настоящей модели — на стенде, файлом диетолога.
