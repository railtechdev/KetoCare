# ADR-0056. Стандарт питания в базе

Дата: 2026-11-09. Статус: принято командой разработки. Этап 2 плана
`docs/PLAN_FOOD_STANDARDS_2026-11.md`, продолжение ADR-0055.

## Контекст

Врач или диетолог должен выбирать, по какому стандарту собирать меню, а клиника — добавлять и корректировать
свои продукты. Сейчас справочник один, название продукта уникально на всю базу, а исключения ребёнка хранят
идентификатор конкретной записи. С несколькими стандартами молоко, исключённое в одном, прошло бы в другом.

## Решение

1. **Продукт принадлежит стандарту.** Новая таблица `food_standards`, у `products` появляется `standard_id`.
   Название уникально внутри стандарта. Рецепты, снимки и ядро по-прежнему ссылаются на `product_id`, версия ядра
   не меняется.
2. **Весь прежний справочник уходит в один открытый стандарт клиники** с постоянным идентификатором. План
   предполагал разнести продукты по источникам и закрыть USDA, это отложено: корректировки копией ещё нет, и
   диетолог потерял бы возможность править продукты. Вид стандарта и закрытость разделены (`kind` и `locked_at`),
   потому что внешний документ сначала загружается и только потом закрывается.
3. **Тождество продукта — общий `food_id`, без отдельной таблицы.** План предлагал таблицу `foods`, но в ней было бы
   только название, которое расходилось бы с продуктами. Новый продукт получает `food_id` записи с тем же названием
   из любого стандарта, иначе свой. Ложное совпадение лишь исключит ребёнку лишнее, в безопасную сторону. Если
   понадобятся группы продуктов, таблица заводится из существующих значений.
4. **Исключения хранятся как раньше и разворачиваются при проверке** на все записи того же `food_id`. Данные детей
   не переписываются, формат ответа API и экранов не меняется. Если продукт переименован в название из другого
   стандарта, объединяются все записи обоих `food_id`: иначе исключение перестало бы действовать на прежние.
5. **Закрытый стандарт отказывает в репозитории** для любой роли. API отвечает 409. Закрыты значения: категория
   остаётся общей рубрикой справочника, и слияние категорий переносит в том числе продукты закрытых стандартов.
6. **Поиск идёт внутри стандарта, по умолчанию основного.** Разбор еды, бот и импорт рецептов остаются на основном
   стандарте. Другой стандарт запрашивает только специалист: параметр от семьи не принимается, карточка записи другого
   стандарта отвечает семье 404.
7. **`fiber_known` определяется стандартом при создании:** если запись углеводов неизвестна, клетчатка неизвестна.

Права врача на продукты, копирование и экраны — этап 3; `patients.food_standard_id` и `menus.standard_id` — этап 5.

## Последствия

- Ответы API получают новые поля, прежние не меняются.
- Счётчики категорий и проверка аномалий смотрят все стандарты. Пока стандарт один, разницы нет; это нужно учесть
  на этапе 3.
- Семья пока может сохранить своё блюдо с записью другого стандарта, если знает её идентификатор. Получить его негде,
  закрыть проверкой состава нужно на этапе 5, где семье понадобятся продукты из меню специалиста.
- Ядро считает, что `carbs_100g` включает клетчатку. Стандарт с `carbs_convention = net` при загрузке нужно приводить
  к этому правилу, иначе клетчатка вычтется дважды. Завести такой стандарт пока нельзя, проверка входит в этап 3.
- **Связь между стандартами держится на совпадении названий.** В документах детсадов названия отличаются от
  справочника («Молоко» и «Молоко 3,2 %»), поэтому перед загрузкой на этапе 4 нужна таблица соответствий: пропущенное
  совпадение означает, что исключение не сработает.
