# 0001. Интерпретация схемы БД в местах, недоопределённых разделом 4.2 ТЗ

## Контекст

Раздел 4.2 ТЗ (`docs/TZ_AI_AGENTS.md`) описывает таблицы через список полей в свободной форме,
без формального DDL. В нескольких местах формулировка допускает более одного разумного прочтения.
Ниже — решения, принятые при реализации `packages/core/src/core/models/`, и почему.

## Решения

### 1. Первичный ключ — uuid `id` на каждой таблице, включая связующие

Раздел 4.1: "Первичные ключи — uuid (генерация `gen_random_uuid()`)" — общее правило для всех
таблиц раздела. Для `parent_patient`/`doctor_patient` в 4.2 показаны только `parent_id fk,
patient_id fk, unique(...)` без явного `id`. Решение: всё равно добавить uuid `id` как PK,
а `unique(a, b)` — отдельным `UniqueConstraint` поверх. Так единообразнее (одна стратегия PK
для всех ~30 таблиц), и сам факт, что ТЗ явно называет unique-ограничение (а не полагается на
то, что PK из пары колонок УЖЕ гарантирует уникальность), читается как сигнал, что PK — это
что-то ещё, то есть отдельный `id`.

Исключение: `link_codes`. Раздел 4.2 описывает её поля как "code (8 симв., unique), parent_id,
patient_id, expires_at (15 мин), used_at" — без `id`, и `code` стоит первым (в отличие от всех
остальных таблиц, где первым явно стоит `id`). Здесь `code` — сам PK
(`packages/core/src/core/models/accounts.py::LinkCode`).

### 2. Дневниковые таблицы: `occurred_at`/`source` — не на всех восьми

Раздел 4.2, группа "Питание и дневники", даёт общую пометку "(у всех: patient_id, occurred_at
timestamptz, source (...), created_by fk users null, deleted_at)" перед списком из 8 таблиц
(`menus`, `menu_items`, `seizure_logs`...`side_effect_logs`). Буквальное прочтение — все 8 полей
получают `occurred_at`/`source`. Решение: применить `occurred_at`/`source` только к шести
таблицам-логам событий (`seizure_logs`, `ketone_logs`, `weight_logs`, `medication_logs`,
`meal_logs`, `side_effect_logs`; общий миксин — `DiaryLogMixin` в
`packages/core/src/core/models/diary.py`), не к `menus`/`menu_items`.

Причины:
- У `menus` уже есть собственный временной якорь — `date` (с `unique(patient_id, date)`);
  добавление второго, `occurred_at`, избыточно и неоднозначно (что означает "occurred_at" для
  плана меню на день?).
- Раздел 4.2 "Индексы" явно связывает `occurred_at` с "дневниками" отдельной строкой:
  "(patient_id, occurred_at) на дневниках" — это ближе по духу к логам событий
  (что-то *произошло* в момент времени), чем к структуре меню.
- `menus`/`menu_items` обслуживаются отдельной группой ручек `/menus` (раздел 5.3), а не общим
  `/patients/{id}/logs/{...}` (который явно перечисляет: seizures, ketones, weight, medications,
  meals, side-effects — без menus).

`patient_id`, `deleted_at`, `created_by` при этом добавлены и на `menus`/`menu_items` — они не
входят в этот конфликт формулировки и однозначно применимы (мягкое удаление — правило 4,
CLAUDE.md).

## Последствия

Если медицинская/продуктовая команда в будущем захочет `occurred_at` на `menus` (например, для
отслеживания фактического времени приёма пищи отдельно от даты меню) — это отдельная,
самостоятельная миграция, не восстановление "как было в ТЗ буквально".
